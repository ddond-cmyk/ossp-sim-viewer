1. 계획의 단위 — 화면이 아니라 「템플릿 + 전개」

132(수행계획수립)가 규모 기준선(본화면 577 · In-Scope 1,020)을 확정했고, 353(UI개발가이드설계)이 구현 원칙을 정했다: 유형 템플릿 7종을 만들고 화면은 데이터로 채운다. 그러면 공수도 화면 수 비례가 아니다.

공수 = 템플릿 7종 (고정비, 高)
     + 변경 화면 107 (신설 57 · 이동 38 · 개명 12 — 개별 작업, 中)
     + 유지·전개 910 (템플릿 적용 + 데이터 검수, 低)

3. 공수 3급 모델

인원·일정 대입 전이므로 급(등급)까지만 확정한다 — 시간 단가는 팀 구성 확정 후 대입.

급대상판정 기준건수
A (개별 설계·구현)템플릿 7종 원형 + 공통 모듈 3종 + 허브 21 + 예외 골격 1새로 만든다32
B (변형 작업)신설 57 + 이동 38 + 개명 12 − A중복템플릿 위에서 개별 판단 필요≈95
C (전개·검수)유지 910 중 잔여템플릿 적용 + 데이터·문구 검수≈893

순서 원칙 3개

  1. A급 먼저, 그중 프로세스형 최우선 — 밸리데이션·상태 밀도가 최고라 템플릿 결함이 가장 비싸게 전파된다.
  2. 지점축 검증은 1지점 완성 → 16지점 일괄 — 컨셉키워드 K2. 지점 accent 대비 검사(354(접근성가이드설계) §3)를 이 시점에 전수.
  3. 예외·안내형(22건 신설)은 A급과 동시 착수 — 컨셉키워드 K4. 늦추면 개발 막바지에 시스템 기본 오류 화면이 노출된다.

4. 원장 작업관리 컬럼 운용 — 341(화면명세서작성)이 숨겨둔 5컬럼을 연다

원장의 담당·상태·설계·디자인·퍼블 5컬럼은 341(화면명세서작성)이 값을 비워서 넘겼다(작업관리는 341(화면명세서작성)의 몫이 아니므로). 여기서 운용 규칙을 확정한다.

컬럼열거값규칙
담당실명배분 단위는 영역(화면구분) — 유형 단위 배분은 담당자가 화면 맥락을 잃는다
상태대기 · 진행 · 검수 · 완료 · 보류보류는 사유 필수(변경근거 컬럼에)
설계·디자인·퍼블— · 진행 · 완료원장이 유일한 진척 SSOT — 별도 진척 시트 금지(이중 관리)

주간 집계는 원장에서 기계 추출한다(상태 컬럼 카운트) — 941(주간보고) 서식의 진척 표가 이 집계와 1:1.

8. 도출 인사이트

관찰 49 — 템플릿 구조가 공수 모델을 바꾼다

화면 1,020개를 화면 단위로 계획하면 균질한 1,020줄 일정이 나온다 — 그리고 틀린다. 실제 비용은 템플릿 32(高) / 변형 95(中) / 전개 893(低) 로 극단적으로 비대칭이다. 상류의 구조 판정(343 매핑표·353(UI개발가이드설계) 템플릿 원칙)이 없었으면 이 비대칭을 계획에 반영할 근거가 없었다. 공수 모델은 일정 기술이 아니라 설계 구조의 반영이다.
